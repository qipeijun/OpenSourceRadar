## 核心分析路径中的问题

### 1. 优先实测的证据门槛不完整（P2）

`src/server/ai.ts` 的 `validateAnalysis` 只要求总体引用含任意公开检索证据，即可接受 `test`。纯函数复现中，八维全部为 `unknown`、需求和缺口未知、只附普通中文介绍，仍可保存“优先实测”。这与需求中“有需求和内容缺口证据”不一致。

应至少阻止需求或内容缺口明确为证据不足时给出优先实测，并区分每项证据支持的命题。当前尚无真实错误 AI 卡，此项是已复现的程序校验缺口。

### 2. 成功检索但无引用导致整个分析终止（P2）

`src/server/ai.ts` 的 `parseSearchResponse` 在搜索已完成但无可用引用时直接抛错；`src/server/service.ts` 随后跳过决策卡。资料稀少的新项目因此只能得到错误，无法形成“本次未找到、缺口未确认、先核验”的有限建议。

应区分外部服务失败和已检索但证据不足，允许后者形成受限判断，不能把无结果自动判作内容空白。

### 3. 弱关键词标签已经决定分析名额（P2）

`src/server/github.ts` 的 `screenProject` 只读简介，按正则顺序匹配场景；`src/server/service.ts` 的 `selectBatch` 直接排除 `other`。纯函数验证：`A compiler for image processing` 被当作内容创作；`A graphical PDF editor powered by a custom rendering kernel` 被判范围外并排除。

实际候选中，游戏开发工作流因 `workflow` 被标为办公，编码 Agent 设计词表因 `design` 被标为内容创作。这些初筛已经标了待核验，但仍会影响名额。弱信号应保留待判断，不能凭单个词硬排除可能符合业务的工具。

### 4. 分析版本不能完整还原输入（P2）

`src/shared/contracts.ts` 和 `src/server/ai.ts` 只保存分析服务、分析模型、规则版本、输出引用及用量；没有保存本次完整输入证据 ID 集合及检索服务/模型。证据虽然追加保存，但无法精确还原某版分析实际看过哪些材料、引用关联摘要由哪个检索模型产生。

应记录完整输入集合和分析/检索两种服务的来源信息。输出引用只是模型选择使用的部分，不等于完整输入。

## 建议推进顺序

1. 重整阅读界面，让候选、分析结论与证据状态一眼可辨，不用原始 JSON 淹没阅读。
2. 修复证据门槛、证据不足的处理、初筛误排除和分析溯源。
3. 配置真实模型与公开检索，先跑通一条真实项目分析，再从系统候选完成10项目试评。
4. 依据真实错误与经营者反馈调整规则，随后补齐每日运行、趋势观测及预测复盘。
