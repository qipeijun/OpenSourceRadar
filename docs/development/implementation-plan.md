## 建议技术方案

建议使用单仓库 TypeScript：React + Vite 网页、Fastify 本地服务、SQLite 持久化。无需首版引入微服务、Redis、容器编排或独立数据库服务器。

Vite 支持前端开发与静态构建，Fastify 承担本地 API 和采集/分析任务，SQLite 适合本机应用持久化。最终依赖版本和 SQLite 驱动在初始化时结合实际 Node 版本锁定，不在本方案硬写未经验证的版本。参考：[Vite](https://vite.dev/guide/)、[Fastify](https://fastify.dev/docs/latest/)、[SQLite](https://www.sqlite.org/whentouse.html)。

前端、服务端按职责分目录，但共享同一套输入输出契约。生产本地运行由服务端提供网页与 API，仅监听回环地址。定时任务在服务端运行，不依赖浏览器页面保持打开；任务状态与实际观测持久化，重启后仅对错过的采集补执行一次。

## 发现与证据来源

1. 第一入口为 GitHub Trending 页面，保存榜单周期、来源 URL、发现时间；解析失败须暴露，不将空解析结果当作无候选。实现时实际获取页面并建立解析夹具；当前未验证实时页面结构。
2. 仓库详情和 README 使用 GitHub 官方 REST API；主题搜索可作后续补充发现源，不替换或伪装 Trending。搜索有数量及独立限流约束，读取响应限流信息，不默认扫描全站。[GitHub 搜索](https://docs.github.com/en/rest/search/search)、[限流](https://docs.github.com/en/rest/rate-limit/rate-limit)。
3. 中文公开检索单独承担证据获取，记录实际执行的查询、来源与读取程度；模型凭知识直接回答不等于完成检索。
4. 建议优先验证 OpenAI Responses 的 web search 作为首个检索能力，分析模型仍可选 OpenAI 或 DeepSeek。官方已提供搜索工具，但账号可用性、引用信息能否满足证据契约，以及中文覆盖须通过实际样本验证。[OpenAI 搜索文档](https://developers.openai.com/api/docs/guides/tools-web-search)。
5. DeepSeek 官方描述了 OpenAI 兼容接入；不能据此推定全部工具或响应字段一致。其文档也提供独立 Search/Fetch 入口，是否用于本项目需进一步核验，不宣称它缺少搜索能力。[DeepSeek 官方入口](https://api-docs.deepseek.com/)。

模型适配与证据获取分别配置。首版先验证一条真实检索路径，不做自动更换供应商、无限重试或多模型并行评审。

## 前后端共同契约

正式实现先以运行时校验定义以下对象，前后端共用类型；不得双方各自发明字段。

| 对象 | 最小语义约束 |
| --- | --- |
| 候选项目 | 稳定仓库身份、URL、来源及发现时间、场景归类及理由；重命名或重复来源不能复制为新项目 |
| 运行记录 | 实际开始/结束时间、当前阶段、已完成与失败项目数、可诊断错误；失败不是空成功 |
| 项目材料与证据 | URL、采集时间、查询、材料版本或摘要、正文/摘要/人工摘录的来源区分、读取限制；未知不填零 |
| 分析版本 | 服务、模型、规则版本、证据标识集合、八维判断、五个选题问题的回答、反证与未知项；新版本不能覆盖旧版 |
| 人工决定 | 对应项目及分析版本、是否实测或继续观察的决定、理由和时间；AI 不得代写或覆盖 |
| 观测与预测 | 指标来源、实际时间、完整性、预测生成时点及期限；禁止未来数据泄漏 |

分析输出先校验结构与引用存在性；是否由证据支持结论另行人工试评，不把 JSON 合法等同分析正确。结构失败保留原因和上一版有效结果。

## 首个可开发里程碑

完成任务草案 T01–T04：系统自动发现真实候选，按场景筛选，检索中文需求与教程证据，生成有依据的选题卡，在本地网页保存经营者判断。T01 可立即实现，不依赖 AI 密钥；T02–T04 的真实联调需要服务配置。

T01 的最低完成标准：无需输入链接即可获得真实候选；展示发现来源与时间；重复采集归并；请求/解析失败与真实空结果区分；基本持久化、API 和网页可验证。只有 T01 完成不能称为选题产品完成。

T05 随后从系统候选选取 10 项试评。自动日程、比较与辅助预测分步补齐，不为等待 7 天历史推迟选题价值验证。

## 协作与验证安排

- 先由后端开发助手确定最小数据契约并实现 T01 采集、持久化及 API；页面开发助手按同一契约实现候选与运行状态。契约确定后两者可并行。
- T02、T03 以独立证据能力并行开发，共用项目身份和材料契约，随后串行整合 T04。
- 跨层完成后由功能验收专家检查自动发现主线、证据限制、人工决定保存和失败状态；共享契约改动安排相应代码审查。
- 自动测试重点覆盖解析失效、去重、引用校验、持久化、AI 失败保留旧版本及恢复补采。接口可通过服务注入测试，前端做组件测试；实际浏览器验证需另有用户授权。
- 本轮仅做文件与文档一致性检查；未启动 dev、未运行浏览器、未调用付费服务、未声称完成真实项目试评。
